# Languages — English and French (Phase 11)

How the three public sites become bilingual, and how the content is translated and
edited. **Decisions of the owner, 2026-10-10 (D89).** Specs of the visible parts are in
`design.md` §13.62–13.63.

## 1. Scope

| In | Out (for now) |
|---|---|
| English (the default) and French, on the main site, Creatives and the Blog | More than two languages (the code takes language codes from one list, so a third is possible later, but is not built) |
| The site's own text, the database content (projects, services, FAQ, experience, certifications, creatives pieces and events, blog posts, settings), emails, the search-engine signals | The admin panel (it stays English) |
| French drafted by Claude, reviewed by the owner (§9) | Machine translation inside the admin; separate French slugs; translated tags; right-to-left languages |

## 2. Addresses

English stays exactly where it is. French is the same page under `/fr`:

| English | French |
|---|---|
| `chestlyace.online/` | `chestlyace.online/fr` |
| `chestlyace.online/projects/slug` | `chestlyace.online/fr/projects/slug` |
| `creatives.chestlyace.online/photography/slug` | `creatives.chestlyace.online/fr/photography/slug` |
| `blog.chestlyace.online/post-slug` | `blog.chestlyace.online/fr/post-slug` |

- Slugs are the same in both languages (one slug per project, post, piece or event).
- `/en/...` is not a public address: it answers a permanent redirect to the same page
  without `/en`, so there is one English address per page.
- The API routes (`/api/…`) and the admin have no language in the address. A request
  that needs text back (the contact form, the newsletter signup) sends `lang` and
  defaults to English.
- The old-address redirects (`ia-content.md` §6) are unchanged and point at English.

## 3. Routing

- Each site's pages move under a `[lang]` segment: `app/sites/<site>/[lang]/…`, and the
  site layout, which writes the `<html lang>`, moves with them. `generateStaticParams`
  returns `en` and `fr`; any other value is a 404. Pages stay statically rendered and
  cached (no `headers()` or cookie read in a page), so French costs no speed.
- `proxy.ts` (`decideRoute`, `lib/sites.ts`) reads the first path segment: `fr` rewrites
  `/fr/x` to `/sites/<site>/fr/x`; anything else rewrites `/x` to `/sites/<site>/en/x`;
  `/en/x` redirects to `/x`. The `?site=` preview override works the same way.
- The language comes into a page as `params.lang` and is passed down as a prop; the
  site chrome (header, footer, theme toggle, particle wordmark) gets what it needs
  through a small context set in the layout.
- `lib/i18n.ts` (pure, tested): the list of languages, `isLang`, `DEFAULT_LANG`,
  `localizedPath(path, lang)` (adds or removes the `/fr` prefix), `switchPath(path,
  to)` and the Intl locale of each language (`en-GB`, `fr-FR`).

## 4. The site's own text

- Every string written in code (menus, buttons, section titles, form labels and
  errors, empty states, the 404 and error pages, the privacy page, "min read", the
  WhatsApp message drafts…) moves to **typed message dictionaries**:
  `content/messages/en.ts` (the English source, which replaces today's
  `content/copy.ts`) and `content/messages/fr.ts`, typed as the same shape, so a missing
  French key does not compile.
- `getMessages(lang)` on the server; a client component gets the strings it needs
  as props from its server parent, so the browser never downloads the whole
  dictionary. `format(message, values)` fills `{name}` placeholders; plurals use
  `Intl.PluralRules`. No new dependency (a library such as `next-intl` is not needed
  for two languages and a static site).
- The defaults of the database-backed settings (the creatives wording, the
  newsletter wording, the hero line) are part of the dictionaries, in both languages.
- Dates, numbers and the reading time use `Intl` with the language's locale.

## 5. The database content

One new column, **`translations jsonb NOT NULL DEFAULT '{}'`**, on every table with
text a visitor reads, shaped `{ "fr": { "<field>": value, … } }`. One mechanism for
every table, no change for English, a migration that only adds the column.

| Table | Translatable fields |
|---|---|
| `profile` (one row) | `headline`, `tagline`, `aboutQuote`, `aboutBody`, `location`, `headlineWords`, `resumeUrl` (a French résumé) |
| `services` | `title`, `description`, `items` |
| `projects` | `title`, `summary`, `description`, `categoryLabel`, `problem`, `approach`, `outcome` |
| `journey`, `volunteering` | `role`, `organization`, `location`, `datesLabel`, `description` |
| `certifications` | `name` |
| `faqs` | `question`, `answer` |
| `design_pieces` | `title`, `category`, `coverAlt`, `description`, `client`, `role`; in `images[]`: `alt` |
| `photo_events` | `title`, `place`, `kind`, `coverAlt`, `description`, `role`, `covered`; in `images[]`: `alt`, `caption`; in `credits[]`: `role` |
| `creative_services`, `creative_faqs` | as `services`, `faqs` |
| `creatives_settings` (one row) | all the wording, including `marqueeWords` |
| `newsletter_settings` (one row) | all the wording |
| `blog_posts` | `title`, `description`, `content`, `coverAlt`, `series`, and `published` (below) |

Never translated: slugs, addresses, images, dates, numbers, tool and technology
names (the tech stack, tools, skills, a certification's issuer), social platforms, and
blog **tags** (the same tag in both languages, so its address is shared).

**Inside the JSON arrays** (`images`, `credits`) a French value is a sibling key:
`{ "alt": "…", "altFr": "…" }`, `{ "role": "…", "roleFr": "…" }`.

**Reading.** Every public read takes the language and passes its rows through
`localize(row, lang, fields)` (pure, tested): for `fr`, each field whose French value
is present and not blank replaces the English one; **anything missing falls back to
English, field by field**, so a page is never empty and the owner can translate
gradually. The cached reads (`unstable_cache`) include the language in their key; the
tags are unchanged, so every admin write still refreshes both languages.

**Blog posts.** The French version of a post is optional. A post is *in French* when
`translations.fr.content` is set **and** `translations.fr.published` is true (so a
French draft can wait). On the French blog every post is listed; one without a French
version shows its English text with a small "EN" mark and the page says (in French)
that the article is only in English; its `lang="en"` is set on the text, its canonical
address is the English one and no French alternate is advertised. The French blog's
feed, tag pages and sitemap list only the posts that have French.

**Admin API.** Each resource's strict Zod schema gains `translations`, an optional
`{ fr: { …the translatable fields, all optional } }` built from the same field list as
the table above, so a field cannot be translated unless it is listed.

## 6. Search engines

- `<html lang="en">` or `fr`; Open Graph `locale` `en_US` / `fr_FR`; the structured data
  carries `inLanguage`.
- Every page that exists in both languages declares `hreflang` alternates (`en`, `fr`
  and `x-default` = English) in its metadata and a self-referencing canonical per
  language. The sitemaps list both addresses, each with its alternates.
- The Blog's RSS feed: `/rss.xml` for English, `/fr/rss.xml` for French (posts with a
  French version only); each page's `<link rel="alternate">` points at its own.
- Titles and descriptions are translated like any text. Nothing redirects a visitor by
  language (§7).

## 7. Choosing the language

- A **language switcher** in the header and the footer (EN | FR, `design.md` §13.62)
  goes to the same page in the other language (`switchPath`); where the page does not
  exist in French (an English-only post) it goes to the French home of that site.
- The choice is remembered in a `lang` cookie (one year, `SameSite=Lax`, no personal
  data). It is used only to stop the suggestion below: **no visitor is redirected
  by language.**
- A **suggestion**: on an English page, for a browser whose preferred language is
  French and that has no `lang` cookie, a slim dismissible line offers the French
  version. It is decided in the browser (`navigator.languages`), so the pages stay
  static.

## 8. Other surfaces

- **Emails.** The newsletter confirmation email and its two pages follow the page
  the signup came from; the contact-form notification and the new-comment email go
  to the owner and stay English. The contact form's confirmation and errors are in the
  visitor's language.
- **The résumé.** `/resume.pdf` serves the English file; `/fr/resume.pdf` serves
  `translations.fr.resumeUrl` when set, else the English file.
- **The particle wordmark and the marquee** take their words from the dictionary and
  the settings (French: DÉVELOPPEUR, DESIGNER, PHOTOGRAPHE). Bebas Neue has the accented
  capitals; the particles are sampled from the same font.
- **Admin** screens stay English; they only gain the French fields (§10).
- **Errors from the API** that a visitor can see (form validation, rate limits) are
  returned in the request's `lang`.

**How the blog does it (11b.4).**

- *Posts.* The editor has an English | Français switch above the details. The French side
  holds the title, description, cover description, series, the body as markdown (with
  "Start from the English text" to begin with the same blocks) and the "Publish the
  French version" switch. The API refuses to switch it on without its text, or with a
  block that cannot be read, exactly as for the English text; a copy of a post brings
  its French along switched off. The posts list marks a post that has French (`FR`).
- *Reads.* `inLanguage` (`lib/blog/localizePost.ts`, tested) is the one place that
  decides which language a post is in; `lang` on the result (`"fr"` or `"en"`) drives
  the `EN` mark, the notice, the `lang` attribute on the English text, the canonical
  address and the structured data. The French blog's tags, tag pages and feed use
  only the posts written in French.
- *The newsletter's wording.* In French a field is: what the owner wrote in French,
  else the built-in French wording when the English field is still the built-in one,
  else the owner's English. The signup sends the page's `lang`; the confirmation email
  and its link's page follow it.
- *Interactive blocks.* The few words a post's blocks and prose carry (copy buttons,
  quiz, terminal, replay, callout labels, the heading link) are in `lib/i18n/ui.ts`.
- *Comments.* A refused comment comes back from the API with a `code` the page words in
  its language; the English `message` is only the fallback. The "Deleted user" name is
  translated by the page. Emails to the owner stay English.

**How Creatives does it (11b.5).**

- *Words in code.* The site's headings, labels, gallery, lightboxes, event pages and
  contact block are in the `CREATIVES_UI` table (`lib/i18n/ui.ts`), read by client
  components with `useCreativesText()` and by pages with `CREATIVES_UI[lang]`; the
  settings' built-in wording is `creativesDefaults` in the dictionaries (so
  `content/copy.ts` is gone). Dates use `Intl` in French (`14 mars 2026`).
- *Settings.* In French a field is: the owner's French, else the built-in French when
  the English field is still the built-in one, else the owner's English; the marquee
  words follow the same rule as a list.
- *Pieces and events.* `localize` for their text, and the French siblings `altFr`,
  `captionFr` and `roleFr` for the pictures and credits. The editors have an
  English | Français switch; the lists show the `FR` chip.
- The site is "Créations" in French; its nav is Réalisations · Design · Photographie ·
  Services.

## 9. Who writes the French

Claude drafts **all** the text that lives in the repository (the dictionaries, the
settings defaults, the seeded creatives services and FAQ), and the owner reviews it in
the pull requests. The owner writes new French content (projects, posts, pieces…) in
the admin.

- **Voice:** the site speaks in the first person ("je"), addresses the visitor with
  **vous** (professional, the owner can change it), plain and warm, no anglicisms
  where a good French word exists.
- **Glossary** (kept in `content/messages/glossary.md` once the build starts):
  software engineer → *ingénieur logiciel*; developer → *développeur*; designer →
  *designer*; photographer → *photographe*; graphic design → *design graphique*;
  event → *événement*; the full album → *l'album complet*; "Get in touch" → *Me
  contacter*; "See the work" → *Voir les réalisations*.
- **Legal text** (the blog's privacy page) is translated but needs the owner's own
  review before it goes live.
- The existing live content in the database (the owner's real projects and About
  text) is **not** in the repository; the French of it is entered by the owner in the
  admin. The editors flag what is missing (§10).

## 10. The admin

(`design.md` §13.63.) In every editor with translatable fields an **EN | FR** switch
at the top shows the same fields for the other language; French fields are optional
and show the English text as their placeholder. Lists get a small **FR** chip (done /
missing) per row and a "Missing French" filter; the settings screens work the same.
The admin's own labels stay English.

The switcher and the search-engine tags ship in the **last** step, so no half-French
site is ever linked.

## 12. Testing

Pure functions with unit tests: `localize` (fallback, blanks, arrays), `localizedPath`
and `switchPath`, the routing decisions, `format` and plurals, the hreflang builder,
the French feed's selection. A **parity test** over the dictionaries: `fr` has every
key of `en`, no empty value, and the same `{placeholders}`. Browser checks of both
languages for each step: the pages, the switcher, a post with and without French,
dark mode, a phone.
